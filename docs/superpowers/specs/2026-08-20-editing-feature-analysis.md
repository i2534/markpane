## 三、逐模块深度分析

### 模块 1：源码视图可编辑化（核心难点）

**现状**：`virtual-source.js` 是**只读虚拟列表**——用一个可滚动 `<div>` 高度撑满，内部按需渲染可视区附近的 `<div>` 行（含行号 `<span>` + 代码 `<span>`）。它**没有任何输入能力**，也**不管理光标**。

**关键事实：虚拟滚动 + 原生编辑 基本不可兼得。** 因为：
- `<textarea>` 无法虚拟化（浏览器必须渲染全部文本才能正确管理光标/IME/选区）
- contenteditable 虚拟化也极其复杂

**两个可选实现路径：**

| 路径 | 具体做法 | 改动量 | 风险 |
|---|---|---|---|
| **B1. textarea 全量渲染** | 源码面板换成 `<textarea>`，放弃虚拟滚动；文件通常 <10MB，可接受 | **中**（重写 `virtual-source.js`，约 200 行） | 大文件（>5MB）编辑卡顿；行号需用 overlay 或放弃 |
| **B2. CodeMirror 6** | 引入 CM6，自带行号/高亮/虚拟化（对超大文件也 OK） | **大**（新增 vendor 依赖 + 集成，约 300-500 行） | 依赖体积 300KB+；高亮与现有 marked 双份 |

> **行号问题**：B1 的 textarea 没有原生行号，需要叠加一个绝对定位的行号栏，并与 textarea 滚动同步——这又是一块改动。B2 免费自带。

**判断**：如果只是"随手改几行"，**B1 足够**，且改动面最小；想要顺滑编辑体验则 B2。倾向轻量，B1 是主推荐。

---

### 模块 2：实时预览管线（数据流反转）

**现状**：`renderMarkdown(text)` 是**全量重渲染**：marked 解析 → 净化 → 高亮 → KaTeX/Mermaid → 行映射 → 目录。只在打开/自动重载时调用一次。

**改动点：**
- 源码编辑 `input` 事件 → **防抖（500ms）** → 重新 `renderMarkdown`
- **性能风险**：每输入一次都全量 marked 解析 + DOM 重建。中小文件（<1MB）没问题；大文件会卡。需要：
  - 防抖已经就位（`debounce` 工具已有）
  - 编辑时的预览渲染应**跳过 Mermaid 重渲染**（很慢，3.5MB 库），只在高亮/普通 markdown 层面
  - **光标/滚动保持**：重渲染会重建 DOM，需要记录并恢复（自动重载已有 `restoreScrollPosition` 可复用，但编辑场景还要**恢复光标位置**——text/CodeMirror 是编辑器自己管理光标，预览侧只需恢复滚动）

**核心取舍**：实时预览的"实时性" vs "大文件性能"。建议：
- 编辑后防抖 500ms 预览
- 显式提供"预览暂停/恢复"按钮（编辑大文件时关闭实时预览）

### 模块 3：写回保存（关键能力）

**现状**：`file-system.js` 只有读（`getFile()`），没有写。`Ctrl+S` 当前导出 HTML。

**改动点：**

1. **`file-system.js` 新增写回**：
   ```js
   export async function saveFile(handle, text) {
     const writable = await handle.createWritable();   // 仅 Chrome/Edge
     await writable.write(text);
     await writable.close();
   }
   ```

2. **保存与自动重载的循环问题**（最容易忽略的坑）：
   - **自己保存**会触发 watcher → 自动重载 → 重新渲染
   - 需要：保存前暂停 watcher，保存完成后恢复；或让自动重载比对"是否是自己的写入"
   - **建议**：保存时 `teardownFileWatcher()`，保存成功后重新 `setupFileWatcher()`（复用现有函数）

3. **`Ctrl+S` 语义变更**：
   - 现状：导出 HTML
   - 改为：**保存原文件**（有 handle 时）
   - 导出 HTML 改到别处（按钮仍保留，快捷键改成 `Ctrl+Shift+S` 或去掉）

4. **降级策略（Firefox/Safari）**：
   - 无 File System Access API → 不能写回原文件
   - 降级为「下载 .md 文件」或复用现有导出 HTML
   - 需要一个明确的保存按钮 + 状态栏提示「当前浏览器不支持写回，已下载」

5. **脏标记/未保存提示**：
   - 编辑后标记 `dirty=true`，标题/状态栏显示 `●`
   - 关闭页面/切换文件前拦截（`beforeunload`）

---

### 模块 4：行映射与同步滚动（从只读解耦）

**现状**：
- `mapping.js` 用 `extractLexerBlocks` + 行号锚定，把渲染块映射到源文本行
- `sync-scroll.js` 监听 `renderBody`/`sourceBody` 的 DOM `scroll` 事件，双向同步

**改动点：**
- 编辑后 `state.rawText` 变化 → 行号全变 → **每次预览重渲染后 `markRenderElements()` 已经重算**（现有逻辑每次 renderMarkdown 都重算，天然适应）
- **难点**：编辑器（textarea/CM）的滚动是它自己的，`sync-scroll.js` 现在只监听 DOM 滚动。需要：
  - textarea 路径：textarea 的 `scroll` 事件 → 同步渲染面板（现有 handler 改成监听 textarea 即可，**改动小**）
  - 从渲染面板点回源码：`scrollSourceToLine` 现在调用 `virtualSource.scrollToLine`，要改成操作编辑器滚动（CM 有 `scrollTo` API，textarea 需算行高）
- **编辑器自身光标行** → 预览高亮（`scrollRenderToMapping`）逻辑可复用，只要把"源滚动位置"换成"编辑器光标行"

| 项 | 改动 |
|---|---|
| 工具栏 | 加「保存」「另存为/下载」按钮（有 handle 才显示保存） |

## 五、成本与风险估算

| 路线 | 预估工作量 | 风险点 |
|---|---|---|
| **B1 textarea + 写回** | 约 1-2 天 | 大文件编辑卡顿；行号同步复杂；IME 兼容 |
| **B2 CodeMirror + 写回** | 约 2-4 天 | 依赖体积；双份高亮逻辑；集成复杂度 |

**关键风险（所有路线共有）：**
1. **保存 ↔ 自动重载循环**——必须做保存时暂停监听，否则每次保存触发一次无谓重载
2. **编辑 ↔ 预览的滚动/光标保持**——重渲染破坏阅读位置，需要细致的恢复逻辑
3. **大文件性能**——实时预览的防抖阈值要可调
4. **Firefox/Safari 写回不可用**——降级 UX 要做好（下载 .md）

## 六、建议的实施顺序（如果将来要做）

```
第 1 步：源码视图 textarea 化（只改 virtual-source.js + 关联 UI）
第 2 步：编辑→防抖预览（app.js 接 input 事件）
第 3 步：写回保存（file-system.js + Ctrl+S + 保存/监听互斥）
第 4 步：行映射/同步滚动适配编辑器
第 5 步：dirty 标记/降级 UX/导出 HTML 移快捷键
```

每步都是**独立可交付**的增量，可以做到一半停（比如只做 1+2 的"无保存编辑"）。
